# Plan: Address as an EVY core resource

## Goal

Today the pickup address lives embedded inside each marketplace item's JSON at
`transfer_options.pickup.address` — there is no schema, no table, no type for it anywhere
(the marketplace `Data` table is free-form jsonb). This plan promotes Address to a first-class
EVY core resource with its own Postgres table in the core (api) database, served through the
existing core-resource CRUD registry and sync loop, and changes marketplace items to carry
`transfer_options.pickup.address_id` (a uuid string) instead of the embedded object.

## Background an engineer needs (read these first)

- **Core resource pattern**: [core.resources.json](types/schema/resources/core.resources.json)
  declares core resources; [generate-core-resources.ts](scripts/generate-core-resources.ts)
  emits TS constants (`EVY_CORE_RESOURCE`) and the Swift `EVYCoreResource` enum.
  [data.schema.json](types/schema/data/data.schema.json) holds the `DATA_EVY_*` row schemas;
  [drizzle.config.json](types/schema/data/drizzle.config.json) maps a `$def` to a Postgres table;
  [generate-drizzle.ts](scripts/generate-drizzle.ts) emits
  `types/generated/ts/db/schema.generated.ts`. Migrations are generated by drizzle-kit into
  [api/drizzle/](api/drizzle) (currently just `0000_baseline.sql`) via `bun run db:generate` in `api/`.
- **CRUD plumbing**: [coreResource.ts](api/src/data/resources/coreResource.ts) provides
  `makeCoreResource` (list/create/update/remove with ajv validation);
  [flows.ts](api/src/data/resources/flows.ts) is the minimal example (5 lines).
  Resources register in `CORE_RESOURCE_REGISTRY` in [data.ts](api/src/data/data.ts:65).
- **Sync is automatic**: [sync.ts](api/src/procedures/sync.ts:29) loops over
  `EVY_CORE_RESOURCE_NAMES` (devices excluded), so a new core resource flows to clients with
  zero sync-code changes. iOS stores synced rows by `(namespace=service, resource)` in
  [EVYDataStore.swift](ios/evy/Data/EVYDataStore.swift); a bare token like `{addresses}`
  resolves through `getJsonForBinding` → `namespace(forSyncedResource:)`, so SDUI can reference
  the new collection by name.
- **SDUI reference-by-id already has a precedent**: items reference conditions via
  `{findFirst(cc2e6c74-…, dc28ed59-….condition_id).value}`
  ([service_sdui.json:52](scripts/fixtures/services/service_sdui.json)). Nested function calls
  work — see `formatDatetime(findFirst(…).data.time, "EEE do")` at
  [service_sdui.json:424](scripts/fixtures/services/service_sdui.json). Addresses will use the
  same pattern with the resource name: `findFirst(addresses, <item>.transfer_options.pickup.address_id)`.
- **The write path is the only genuinely new machinery.** Today the Search row
  ([EVYSearch.swift:93-99](ios/evy/UI/Views/EVYSearch.swift)) dumps the whole `place_search`
  datum into the item's draft/record at `{…transfer_options.pickup.address}`. Actions
  (`create`/`update` in [EVYActionRunner.swift](ios/evy/UI/EVYActionRunner.swift:94)) can create
  or update any resource and DO sync to the server (`syncMutation` in
  [EVY+Mutations.swift](ios/evy/Core/EVY+Mutations.swift:16)), but `create()` generates the new
  uuid internally and never exposes it — so today a flow cannot link a freshly created record
  to another record. This plan adds an optional 4th argument to `create()`:
  `create(service, resource, {data}, destinationPath)` which writes the new record's id to the
  destination (draft-aware, same write path as row destinations).
- **Two address shapes exist today** and this plan unifies them:
  - RPC shape from [placeSearch.response.schema.json](types/schema/rpc/placeSearch.response.schema.json):
    `id` (Google place id — NOT a uuid), `unit`, `street`, `city`, `postcode`, `state`,
    `country`, `latitude`, `longitude`.
  - Fixture item shape ([service_data.json:119](scripts/fixtures/services/service_data.json)):
    same fields minus `id`, plus `instructions`.
  The core `DATA_EVY_Address` uses the union: uuid `id` + all address fields + `instructions`
  + timestamps. The Google place `id` must never be written into an Address record — the new
  SDUI wiring copies fields explicitly, which excludes it naturally.
- **Docs to skim**: [docs/evy/data.md](docs/evy/data.md), [docs/evy/sdui.md](docs/evy/sdui.md),
  [docs/evy/functions.md](docs/evy/functions.md), root [README.md](README.md), [AGENTS.md](AGENTS.md).

## Design decisions (locked in unless review objects)

1. **Resource name** `addresses` (singular `address`), core service `475731ac-31aa-4d65-94d2-7032782ae359`.
2. **Schema** `DATA_EVY_Address`: required `id` (uuid), `createdAt`, `updatedAt`; optional
   `unit`, `street`, `city`, `postcode`, `state`, `country`, `instructions` (strings) and
   `latitude`, `longitude` (numbers). `additionalProperties: false`. Optional-by-default because
   manual text entry (`buildAddress`) produces partial addresses; place search guarantees more
   but the store shouldn't reject drafts.
3. **Item shape**: `transfer_options.pickup.address` (object) → `transfer_options.pickup.address_id`
   (uuid string). `instructions` moves onto the Address record (it describes the address).
4. **One Address row per item** in fixtures (the two seeded items currently duplicate the same
   address). Reference semantics make a shared row a footgun: editing item A's address would
   silently change item B's.
5. **Registry registration**: register the full `makeCoreResource` factory object (list, create,
   update, remove) like flows/pages/rows.
6. **Write path**: Search row writes the picked place into a page-local draft `pickup_address`
   (same pattern as the existing buyer-side `shipping_address` local var); the Instructions input
   reads/writes `pickup_address.instructions`; a Save action then either
   `update(core, addresses, {id: <address_id>}, {…fields from pickup_address…})` (id already set)
   or `create(core, addresses, {…fields…}, <item>.transfer_options.pickup.address_id)` (new).
   `update()` needs no changes; `create()` gains the optional id-destination argument.
   This is a small, deliberate UX change: address edits commit on Save instead of continuously.
7. **No Swift model codegen changes needed**: iOS consumes data dynamically as `EVYJson`; only
   `CoreResources.generated.swift` changes (regenerated enum case `addresses`).
8. **SDUI condition strings must not use quoted literals** (`{x == "y"}` silently never matches);
   any new conditions use unquoted literals / `length(...) > 0` / findFirst pairs.

## Risks & open questions

- **UX change**: address edits now commit on Save instead of write-through. Flag in the PR.
- **Orphaned Address rows**: deleting an item does not delete its address (no cascade across
  databases). Acceptable now; note as follow-up.
- **`create()` 4-arg parsing on web**: the builder may treat action strings as opaque text — if
  so, step 28's builder change is a no-op. Verify rather than assume.
- **Seeding `pickup_address` when reopening the sheet** (step 26): if the interpolation layer
  can't seed a local draft from `findFirst(...)`, fall back to sourcing the Search/Input rows
  from the saved record for display and only writing drafts on change.
- **Fixture uuids**: new address ids and the `coreAddressesResource` service-resource id must be
  freshly generated uuids — do not reuse existing fixture ids (pages are stored globally by id).
